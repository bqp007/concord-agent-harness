# Security policy

## Reporting a vulnerability

Please report security problems privately, not in a public issue. Use GitHub's private vulnerability reporting (the **Report a vulnerability** button on this repository's Security tab). Include the version or commit, what you ran, what happened and, if you can, a minimal reproduction.

Concord is maintained by one independent developer. Reports are acknowledged within seven days on a best-effort basis, and confirmed problems are fixed in the next release, with credit if you want it. There is no bug bounty.

Only the latest release on the default branch receives fixes.

## What Concord is, and what it is not

Concord is a workflow harness, not a sandbox. The agents it starts (the planning session, the executors and the reviewers) run with your user account's permissions: they can run shell commands, read what your account can read and reach the network through their harness. Plans, prompts, diffs and repository notes are sent to the model providers you configure.

The dispatcher enforces the plan approval, the red run, the out-of-scope report, the PASS rule, the review tier, the billing guard and an allow-list of the environment variables an executor receives, which never passes `ANTHROPIC_*`, `CLAUDE_*` or `CLAUDECODE`, even when `executors.conf` lists them. Everything else it relies on (the executor contract, the hook rules) is an instruction that a model can ignore, and the hook rules catch only common spellings of the commands they name.

## Known limitations

- File scope is enforced for an executor's edit tools on OpenCode only. A shell command, such as a redirection, can still write outside the phase's files. Changes inside the repository show up in the out-of-scope report after the run; outside it, only the watched files listed below are compared.
- On OpenCode, executors may run any shell command except a short deny list (deleting files, changing branches or git state, committing, pushing, `sudo`); other harnesses apply their own permission settings.
- On macOS, Concord runs the OpenCode and pi executors under a Seatbelt profile (`concord/opencode.sandbox.sb`). It denies reads of credential stores and private data (`~/.ssh`, `~/.aws`, `~/.config/gcloud`, `~/.config/gh`, `~/.gnupg`, `~/.docker`, `~/Library/Keychains`, `~/.netrc`, `~/.npmrc`, `~/.pypirc`, `~/.git-credentials`, the Hugging Face token files, `~/.kube`, Claude Code's `~/.claude.json`, transcripts, session data and history, and the paths `opencode.sandbox_deny` lists) and allows writes only to the worktree, OpenCode's data and cache folders, `$TMPDIR` and the standard streams, never to the repository's Git directory. Every other file your account can read stays readable, OpenCode's own credentials included, and the network stays open. The profile is skipped on Linux and inside another Seatbelt sandbox, such as a Claude Code shell, and `--no-sandbox`, `CONCORD_NO_SANDBOX=1` or `opencode.sandbox = no` turn it off. Under it, OpenCode's cache folder, `$TMPDIR` and, for a run in the main checkout, other tickets' worktrees stay writable.
- The red run, the characterization, the acceptance commands, the static checks and every later test run execute the checkout's code as your user, with your environment (less the Claude and Anthropic variables), the network and the repository's shared Git metadata, unsandboxed on every platform. They run in a temporary Git worktree of the run's tree, which keeps the graded evidence apart from the checkout but confines nothing: `git checkout-index` applies the repository's configured filters there, and a command can write to the checkout, the Git directory or anywhere your account can. What they write to the checkout, its Git state or a watched file counts against the run or refuses its PASS; other writes go unseen.
- Concord hashes a fixed set of files outside the checkout before each run, after it and again at PASS: its own `*.py`, `*.md` and `*.conf` files, the repository's notes, `~/.claude/CLAUDE.md` and `settings.json`, the top-level files of `~/.claude/agents/`, `commands/` and `hooks/`, OpenCode's `~/.config/opencode/*.json` and `*.jsonc`, and, from a worktree, the main checkout's `.claude/hookify.*.local.md` and `.claude/settings.json`. It hashes the Git directory's `config`, `info/exclude`, `info/attributes` and hooks folder the same way, and scans each linked folder for files whose modification or change time falls within the run, up to 200,000 entries; such a file counts against the run, whoever wrote it. This detects a change after the fact; it does not prevent it. Every other path outside the checkout goes unwatched, among them the skills, nested command folders, the Seatbelt profile, a custom Git hooks path, the plugin's files and the review records under `<git-common-dir>/concord/`, which the PR gate reads. The start state that grades a run stays in the dispatcher's own memory.
- Concord keeps copies of what it handles. Each run folder under `<git-common-dir>/concord/` holds the executor's prompt, its raw output, the red-run and acceptance output tails, backups of the in-scope files and the pinned grading inputs; review packets and answers, with their reproductions, sit beside them, and nothing is pruned. The runs folder and each run folder are created owner-only (0700); the files inside keep your umask's mode, and a runs folder made by an earlier version keeps its mode. Capturing a tree writes the contents of untracked files that are not ignored, a secret among them, into the repository's object store, where they stay until `git gc` prunes them. The prompt is also an argument on the executor's command line (`cmd.json` records the command with the prompt left out), and the pi executor's session files stay in a `concord-pi-*` folder under `$TMPDIR`. Delete these yourself after a run that handled something sensitive.
- The billing guard reads the model id's text. A harness bills the route its model id names, with the login or key it reads itself; Concord does not see the provider or the account, and a name that resolves to a paid route runs without a prompt, since asking first is an instruction to the planner.
- `install.sh` adds `sandbox.excludedCommands` entries to `~/.claude/settings.json`, so `gh`, `git push`, `git fetch`, `git pull` and `git clone` run outside Claude Code's sandbox in every project. Remove them if you do not want that; each later install adds back the ones it finds missing.

## Recommendations

- Run Concord where the agents cannot reach credentials you would not hand them: no production keys, cloud administrator tokens or SSH keys to systems that matter. A disposable container or virtual machine is the safest place for an untrusted repository.
- Keep secrets out of plans, repository notes and prompts.
- Read every diff before you commit. Concord never commits to a branch or pushes (`wt.py fork` writes only an unreferenced snapshot commit object); keep it that way in your own setup.
- Keep the dispatcher and the plugin up to date.

Problems in the model providers or agent harnesses that Concord drives belong with their maintainers.
