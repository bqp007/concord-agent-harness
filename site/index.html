Who decides, who writes, who judges

Coding agents now write code faster than people can read it. Review quietly turns into approval, and after a few weeks nobody can say why the system is shaped the way it is. Concord spends your limited attention where it matters, and gives each of three roles its own place in the loop and its own limits.

Who decides

You. You answer the planner’s questions, give one go/no-go on the plan and make the commit. Consequential behavior and architecture choices come to you, however small the change.

Who writes

A strong model plans each change, has the failing tests written first, writes the small fixes and checks every result. In delegate mode, low-cost models write the bulky phases inside the files each phase declares.

Who judges

A verifier that did not write the plan challenges it, and a reviewer that did not write the change reads it at its risk tier. The dispatcher, not the writer, runs the acceptance commands and refuses a PASS without their expected results.

The is concord.py, a standard-library Python script. It enforces what a prompt alone cannot: a plan approval bound to the hash of the plan text the read, a before any code, a checked against snapshots of the checkout, acceptance results taken on a copy of the , review tiers, and a of every verdict with its cause.

Each ticket runs in one of two modes. In the planning session writes every phase; in each phase goes to the the plan assigns, free tiers first for the bulky ones. The loop around the writing is the same in both.

How it works

Ten steps, numbered as in the figure. The example is the credential-free demo that ships with the repository: a toy shop whose cart total ignores the quantity of each item.

1. Plan, or split a large ticket

Work starts in Claude Code with /concord:run execute <task> or /concord:run delegate <task>. The planner reads the code, the spec, any Cases: file and the skills once, then writes an early PLAN_<ticket>.md: a Done when line, the design, a Test plan, conflicts between sources, open questions, and per phase its executor, risk, files, follow-through files, steps, size and dependencies.

A phase’s Follow-through: line names the files that change only because the phase’s change requires it, such as the docs that describe the changed code, so you approve them with the plan. A ticket whose parts can land and be reviewed apart gets a split plan instead: a table of child tickets cut along their seams, verified and approved once, after which each child runs this loop with its own plan and go.

2. Questions

Before anyone checks the plan, the planner asks at most five blocking questions, each with a default. This is the first point where you take part: you answer the questions, or let the defaults stand. Choices the code cannot settle are listed under ## Open questions in the plan.

3. An independent verifier

concord.py --lint checks each phase without a model call and writes the : the approval-relevant text of the plan, saved under a name taken from its hash. The plan-verifier agent reads that file and checks the plan against the code by reading it: that every item serves the goal, that its claims about interfaces and callers are true, that each acceptance command would fail before the work, and that each Risk: fits what the phase touches. It answers with CUT, MERGE and FIX items.

--plan-verdict records an APPROVE answer that quotes the plan read’s hash, and it holds only for text with that hash: the plan without the prose of its Open questions, Handoff and Passes sections, read line by line so that line endings do not change it. An answer with more than one VERDICT or PLAN-HASH line records nothing. The dispatcher checks the hash, not who wrote the answer. Every run reads the plan once and checks that text against the approved revisions; a run whose plan text has none exits 11, and no words of yours open that gate.

4. Your go

concord.py --estimate turns each phase’s Size: and After: lines and the run ledger into lanes, a critical path and an ETA. You then give one on the lanes, the ETA and the verifier’s cuts.

The go holds while the work stays as you saw it: when a later fix changes anything in a phase beyond who writes it, its size, its wait, its notes or its risk, the planner shows you the change and asks for that phase’s go again. The dispatcher requires a recorded APPROVE of the plan text, though it cannot tell who wrote it; your go is a stop that the planning session’s instructions require.

5. Tests that fail first

For each changed behavior, tests that fail on the current code are written in their own run, and the planner checks that each one fails for the stated reason before any implementation starts. A routine change under characterization checks needs no separate red run.

The phase’s then serve as the red run. Before an executor starts, the dispatcher runs them on a copy of the untouched tree; a delegated phase whose acceptance already passes is not run (exit 6), because its tests do not test it. In execute mode the session run starts with a warning instead.

6. Implement

In execute mode the planning session writes each phase inside a recorded --begin/--end run, which takes the same backup, scope report and checks as any other run. In delegate mode the planner still writes what costs less to write than to specify, and concord.py <model> <phase> runs each bulky phase on a low-cost model, free tier first.

An executor reads the run’s snapshot of the approved plan, never the plan file, and a shared contract that tells it to change only its phase’s files. On OpenCode, edits outside the phase’s Files: and Follow-through: are refused during the run; on other harnesses the report’s out-of-scope lines catch them. A lock covers a set of files rather than a checkout, so phases whose files are disjoint run in one worktree at the same time. In the demo, the first attempt also edits a file outside its scope:

7. Check

After the run, the dispatcher compares the checkout with the start state it kept in its own memory, where the executor cannot rewrite it. A change outside the write scope, the deletion of a file outside it that is not build output, any change to the index, an executor’s edit of the plan, or a moved HEAD rejects the run: no post-run command runs and there is no candidate. The red run ran on a copy of the start tree after that start state was taken, so what it changed counts too. Otherwise the checkout as the writer left it becomes the run’s candidate, and the acceptance commands run on a copy of it.

The report comes from these snapshots, never from the writer’s account. A PASS needs the expected result of every acceptance command, in a checkout that still holds the candidate and the state it was graded in; otherwise --verdict PASS exits 7. A FAIL is recorded with its cause, and only EXECUTOR failures count as attempts: after three, the planner stops and asks you.

8. Review by risk tier

The phase’s Risk: line sets the , and the tier sets who reviews. High risk means untrusted input, scores or thresholds, security, money, data deletion or concurrency.

Low

A flash model, which judges BLOCKER and HIGH findings only.

Medium, the default

Opus 5.5, as an independent reviewer agent.

High

Opus 5.5 and a flash model from another family, at the same time; their blind spots differ.

A finding needs a reproduction to stay above NOTE. Confirmed findings are fixed, then a cheap shows which findings the fix closed; the loop stops at zero open BLOCKER, HIGH and clause FAIL findings. Before merge, concord.py --pr-status exits 0 only when every file of the current diff is covered at its tier and no BLOCKER, HIGH or clause FAIL is open; there the dispatcher closes a finding when a later review cites the lines that fix it.

9. Report

Once every run of the plan has a verdict, concord.py --report writes the test report from recorded data, stops the drift clock and closes the plan to new runs: a later run on it exits 10. The report opens with the : each forced PASS beside its failed commands, each PASS with no acceptance command, each skipped red run, each waiver and owner go-ahead, and each PASS whose phase a later revision changed. Then come the phases, with who wrote each, the plan revision its run followed, the graded candidate and its latest review.

10. Your commit

The session replaces the repository notes the ticket changed and merges the approved case changes into the Cases: file. Then you commit and merge. The dispatcher never commits to a branch, pushes or changes branches in your checkout (wt.py fork writes only a snapshot commit object that no branch or ref points to); the planning session is told not to, by an instruction rather than by code.

Principles

Seven promises. Each names the mechanism that enforces it, a refusal you can reproduce with concord.py, and the limit that remains.

P1Runs follow the approved plan textexit 11
Mechanism
--lint writes the plan read under a name taken from its hash; the verifier’s answer quotes that hash, and --plan-verdict records an APPROVE that quotes it as an approved revision. Each run checks its plan text against those revisions, and the executor reads the run’s snapshot of the approved text, never the plan file.
Refusal you can reproduce
--begin or an executor run exits 11 when the plan text has no APPROVE, or when the stored plan read changed after it. No --user-approved words open this gate.
Limit
The dispatcher checks that a recorded APPROVE quotes the hash of this plan text; it cannot tell who wrote that APPROVE, and the demo records a scripted one. It does not record your go either: your go/no-go is a stop in the planning session’s instructions. The prose under ## Open questions, ## Handoff and ## Passes is left out of the approved text.
P2Tests fail before the code existsexit 6
Mechanism
Before an executor starts, the dispatcher runs the phase’s acceptance commands on a copy of the untouched tree: the red run. A command marked (characterization) guards existing behavior and is expected to pass.
Refusal you can reproduce
A delegated phase whose acceptance already passes is not run: the dispatcher prints NOT RUN and exits 6.
Limit
The red run shows that a command fails, not why; the planner checks the reason. In execute mode a session run warns instead of refusing, and --force runs a delegated phase anyway, with the run noting it.
P3A PASS rests on recorded resultsexit 7
Mechanism
The dispatcher takes the checkout the writer left as the run’s candidate, runs the acceptance commands on a copy of it and writes the report from snapshots of the tree.
Refusal you can reproduce
--verdict PASS exits 7 when an acceptance result is missing or not the expected one, when a post-run command changed the tree, or when the checkout no longer holds the graded candidate and the state it was graded in.
Limit
The acceptance commands are only as strong as the tests the plan names. --force records a PASS (forced), and the report lists it first, under Overrides, as it does a PASS with no acceptance command.
P4Each phase declares its files firstrejected, exit 7
Mechanism
Each phase lists its Files: and Follow-through: in the approved plan. The run lock covers those files; after the run, a change outside them, the deletion of a file outside them that is not build output, any change to the index, an executor’s edit of the plan or a moved HEAD rejects the run, which then has no candidate. On OpenCode, edits outside the scope are refused during the run.
Refusal you can reproduce
The run report prints REJECTED (not graded), and a PASS on that run exits 7. bash scripts/demo.sh shows it.
Limit
During a run, scope is enforced only by OpenCode’s edit tools, not shell redirection. On other executors an out-of-scope edit is caught after the run, and the backup of in-scope files is the safety net.
P5Review rises with riskexit 1
Mechanism
The phase’s Risk: picks the tier: a flash model at low, Opus 5.5 at medium, Opus 5.5 and a flash model from another family at high. At the merge gate every file needs a review at its tier, and a finding stays open until a review of a later head shows it fixed.
Refusal you can reproduce
concord.py --pr-status exits 1 until the current diff is REVIEWED; --review-pr --tier below a file’s needed tier is refused (exit 2).
Limit
A review covers only what its reviewer could read, at the rank of the reviewer name the planner records, and a binary file needs your words naming it. At the low tier the reviewer may run on the same low-cost model as the executor, in a fresh context.
P6Every run is recorded; overrides come firstexit 2
Mechanism
Every run and verdict goes to a ledger, a FAIL with its cause: EXECUTOR, PLAN_GAP, TEST_DEFECT, FLAKY, PROVIDER or BLOCKED; only EXECUTOR counts as an attempt. --report writes the test report from recorded data and opens with the overrides: each forced PASS beside its failed commands, each waiver and owner go-ahead.
Refusal you can reproduce
--report refuses while a run of the plan has no verdict (exit 2). Once the report is written, a new run or --begin on that plan exits 10.
Limit
The planner alone assigns the failure causes. A FAIL recorded without a cause gets only a reminder. The report is a status export: it does not check that every phase passed.
P7You commitrejected, exit 7
Mechanism
The dispatcher never commits to a branch, pushes or changes branches in your checkout (wt.py fork writes only a snapshot commit object that no branch or ref points to), and the planning session is told not to. A run that changes the index, moves HEAD or changes the branch is rejected, and OpenCode’s rules deny an executor git commit, git push and similar commands.
Refusal you can reproduce
The run report lists the staged path or the moved HEAD as a rejection, and a PASS on that run exits 7.
Limit
No code stops the planning session from committing outside a run: that rule is an instruction in Concord’s Claude Code rules and the run command, and the dispatcher sees a moved HEAD only inside a run. Outside OpenCode, the git rules in the executor contract are instructions a model can ignore too: a commit during a run is caught after the run, not prevented. wt.py new creates a branch and a worktree per ticket when you ask.

How it differs

Concord learned from other workflows and papers. Read against the same four questions, the kinds of harness differ mainly in where a person decides and in what code, rather than a prompt, enforces.

Method. The rates are per checkout. An attempt is a run with a verdict on a phase in one checkout, by any runner and after any cause of failure (81 of the 86 later passes were executor retries); a run a model provider refused (111 runs, left out of every count), a refusal at the red-run gate and a run without a verdict are not attempts. A later attempt starts with the evidence of the failed one; the workflow’s own three-failure stop, an instruction in the plugin from 3.0, counts only EXECUTOR failures. 499 of the 696 phases (72%) received a PASS as their earliest recorded event of any kind; 41 began with a provider refusal and 30 with a refusal at the red-run gate. The record spans Concord from its pre-release versions to 3.2, and the checks described above took their present form in versions 3.0 to 3.3 (21 to 27 November 2026), so most recorded runs passed under earlier, looser checks; of the 585 first-attempt passes, 386 kept a run record, and 286 of those show every acceptance command with its expected result and no forced verdict. Of the 111 phases that failed their first attempt, the planner labeled 59 of those failures as the executor’s work, 33 as a gap in the plan and 19 as a blocked run, a test defect or a flaky check.

The executor charges apply list prices read on 28 November 2026 to the recorded tokens (uncached input, cache reads, cache writes, which are zero in every measured executor run, and output) of the 866 executor runs with a verdict, failed attempts included, divided by the 671 executor phases with a recorded PASS; 5 of those 671 got their first PASS from a Claude run whose cost is not in the numerator. For 180 runs the split between token kinds is estimated from measured runs of the same executor and model family, and 12 verdict runs without a token record count as zero. The repriced rows do not model how another model would have done the work. A frontier model wrote the plan, the file scope and the failing tests before an executor started. Planning, checks and reviews by Claude models, and the phases Claude models wrote, ran on a flat-rate frontier subscription. Matched Claude Code activity plus executor verdict runs, at list prices from the session transcripts, comes to US$6 to US$9 per phase with a recorded PASS (1,016 phases, any runner) in three matching scenarios, and executors are 0.7 to 1.1% of these charges. Not in these charges: reviews on low-cost models (US$31.69 at list prices for those with a token record), executor runs without a verdict (US$15.16), provider-refused runs, human time and subscription spend. Install

Concord installs from a clone. To see every link, copy and backup before anything is written, run bash install.sh --dry-run first.

1 · Clone the repository 
git clone https://github.com/bqp007/concord-agent-harness.git && cd concord-agent-harness
2 · Install into Claude Code 
bash install.sh

The default install links the commands, agents and skills into ~/.claude, installs the dispatcher and runs its suites. It also writes the Concord rules into ~/.claude/CLAUDE.md between markers and adds missing keys to ~/.claude/settings.json, including entries that let gh and git push, fetch, pull and clone run outside Claude Code’s sandbox. It backs up each file it changes. Restart Claude Code afterwards.

Try it without credentials 
bash scripts/demo.sh

The demo runs the whole loop in both modes in about a minute, inside a temporary folder, with a scripted executor instead of a model: no network, no account, nothing left outside that folder. Add --keep to inspect the run folders afterwards.

Requirements

  • macOS or Linux, bash 3.2 or later, git, and Python 3.9 or later (standard library only)
  • Claude Code, for the commands and agents
  • The demo needs only bash, git and Python

Low-cost executors

  • OpenCode for the free tier, the one path where out-of-scope edits are refused during the run
  • The pi CLI for models on the OpenCode Go allowance
  • Without either, Claude subagent phases, verdicts and the medium-tier review by reviewer-opus55 still work; the low-tier review and the second review from another model family that a high-risk change needs cannot run

Not a sandbox. Agents run shell commands as your user. On macOS the OpenCode and pi executors run under a Seatbelt profile, which is skipped on Linux and inside another sandbox; the red run and the acceptance commands run the checkout’s code before and after each run, unsandboxed, with your environment. Known gaps and how to report a vulnerability: SECURITY.md. Setup details: docs/SETUP.md.
