---
description: Run plan phases on their executor or a named model, check each result, review, fix confirmed findings
argument-hint: [model] <phase | 1,3 | 2-4 | all> [feedback | escalate]
---
Rules: CLAUDE.md. Arguments: $ARGUMENTS. Chat: lean STE (tables); commands, plan text, code: full. Flags, limits and exit codes: `python3 ~/.claude/concord/concord.py --help`.

## 1. Resolve
- Plan: the `PLAN_<ticket>.md` the request names, else the only one at the repo root, as `--plan <file>` on every call; none → offer `/concord:plan-then-delegate`.
- Model: the request, else `Executor:`, else models.conf `default`, checked with `concord.py --resolve "<name>"`; ask when unknown or ambiguous.
- Every run needs the verifier's APPROVE for the plan's current text (exit 11 otherwise): after an edit, `--lint` again, re-verify, `--plan-verdict`.

## 2. Run (only real dependencies wait: CLAUDE.md, `/concord:plan-then-delegate` step 3)
- The run lock covers each run's `Files:`: executor phases with disjoint `Files:` run in the ticket's worktree at once; a run with no `Files:`, or one that shares a file with a running phase, is refused. An open `--begin` run blocks every other run in its checkout, so executor phases that run beside a planner phase, or that share a file, get a fork: `python3 ~/.claude/concord/wt.py fork <TICKET> <N>`, run and checked there with `--repo <fork>`; after PASS, `wt.py join <TICKET> <N>` from the checkout that made the fork applies its changes back and removes the fork. Join refuses, and keeps the fork, when the fork holds a file in two versions (staged or committed content that differs from the working file) or ignored files of its own; `--force` joins anyway and lists what it drops. Reviews, lints and suites take no lock.
- `planner` phase: `--begin <phase>` first (it starts the drift clock and passes the gates), write it, re-run its acceptance, `--end <run-id>`.
- Claude subagent: `--begin <phase> --label <name>`, the subagent (plan path, the approved revision path that `--begin` prints as `approved plan`, phase, feedback), `--end <run-id>`.
- OpenCode or pi: `concord.py <model> <phase> --plan <F> [--extra=<feedback>]`, background, outside the sandbox; red-run exit 6 (acceptance already green): TEST_DEFECT, or mark it `(characterization)`. File scope is enforced only on OpenCode; on pi the report's out-of-scope lines are the check.

## 3. Check (each run)
- Failing report lines: OUT OF SCOPE (source), DELETED, STAGED BY EXECUTOR, GIT INTERNALS CHANGED, PLAN FILE MODIFIED, HEAD MOVED, BRANCH CHANGED, CHARACTERIZATION CHANGED, ACCEPTANCE FILES CHANGED, ACCEPTANCE COMMAND CHANGED GRADING FILE, OUTSIDE CHECKOUT CHANGED by the executor, STATIC NEW, ACCEPTANCE AFTER RUN: 0/N, RESOURCE LIMIT (the line names the cause). `EXECUTOR BLOCKED` → FAIL BLOCKED; `PROVIDER LIMIT` or `PROVIDER BLOCKED` → FAIL PROVIDER, then the next model; on a review (exit 9) nothing is recorded, so the next model reviews; an OpenCode refusal of an unlisted file without a BLOCKED line → PLAN_GAP.
- Trust the report's `acceptance after run` line (the dispatcher re-ran the acceptance); re-run only to settle a doubt (a flip on rerun: FLAKY). Read `git diff HEAD -- <the phase's files>`: out-of-scope source, or tests an implementing phase touched, fail it. No full suite and no review before §5.
- PASS when every acceptance command has its expected result after the run and the diff matches the phase: `--verdict <run> PASS`. The dispatcher refuses it (exit 7) when a result is missing or unexpected, or an acceptance file changed during the run or the post-run acceptance commands. A `(fails until …)` command counts as red only on a real failure, not a timeout or a command that could not run; its phase needs `--note "<the tests that failed and why>"`, after you checked each fails for the stated reason. `--force` records `PASS (forced)`, which the report lists under Overrides with the failed commands beside your `--note` as the reason (`reason: not recorded` without one).

## 4. FAIL
`--verdict <run> FAIL --cause <CAUSE> --note "<why>"`.
- EXECUTOR: retry the same model with `--extra="EVIDENCE: <command + decisive lines> | SUSPECTED: <files> | CHANGE: <what must differ>"`; after three EXECUTOR failures of a phase, stop and ask the user. Escalate (models.conf `ladder`) only when the user asks.
- PLAN_GAP: `--restore <run>`, fix the plan (ask on the user's calls), re-verify it, retry.
- BLOCKED: answer in the phase's Decisions (ask on the user's calls), `--restore <run>` if files changed, re-verify, re-run with `--extra "ANSWERS: ..."`; a second BLOCKED is a PLAN_GAP.
- TEST_DEFECT, FLAKY: fix the tests here. Out-of-scope edits, deletions or a modified plan: stop, show them, offer `--restore`.
- `--restore <run>` works only in the checkout of the run and restores only files still as the run left them (content, type and executable bit); it lists the others and leaves them alone.
- A defect found after the gate (a later review, a PR comment, production) is fixed with a test or lint that fails on the old code, never a REVIEW.md line.

## 5. Full revision
- Large or risky work: start the independent review at the first coherent snapshot, with your own checks beside it; later edits get a delta review or a re-review.
- After the last phase: consolidate the tests the ticket touched (keep each test that catches a failure the rest would miss; only this session merges or deletes tests, naming the remaining test that catches what each removed one caught), then at once every suite (one checking the checkout itself, such as `tests/demo_test.sh`, alone) and the review of the whole diff: the PR gate (§6), else each implementing run's review.
- Review loop: a full review → fixes → a delta review of the fix, which closes each finding it shows fixed; whatever the delta does not explain needs a review at its own tier; stop at 0 open BLOCKER and HIGH. Fix BLOCKER and HIGH, and a MEDIUM only when it occurs in a real flow; the other MEDIUMs and the NOTEs go to the test report (§7).
- Tier = the phase's Risk (default medium), raised for matching non-test files by a repo-notes `Risk floor <tier>: <globs>` line. low: `concord.py --review <run>` (flash), approve-only: it judges BLOCKER and HIGH only, keeps a MEDIUM it reports as a note, and its clean verdict reads `CLEAN at low (BLOCKER and HIGH only)`. medium, high: `--review <run> --packet`, a fresh `concord:reviewer-opus55` Agent per round, `--review-record` its answer with `--tokens <the Agent's total_tokens>`. A phase reviewed below its Risk, or not reviewed, is listed under Overrides in the report. Over the packet cap: `--files <globs>` per group.
- Review a fork (`wt.py fork <TICKET> <N>` with a number no phase uses); Monitor `<packet>.stream`, fix each streamed finding in the ticket worktree as it lands (small: here, else its executor, `--extra`); one delta review after the final verdict. Every delta review runs on flash, else on the `concord:reviewer-delta` agent, never on Opus.

## 6. PR gate
- Review the PR's diff from its merge base to its current head. Each file needs the highest `Risk:` of this PR's runs that changed, created or deleted it (medium when no run touched it; never below a repo-notes floor). `--review-pr <PR>` runs at the highest needed tier of its files; `--tier <T>` below a file's need is refused. Phase reviews do not count here.
- `--review-pr <PR>` runs flash; `--packet` for `concord:reviewer-opus55`. Over the cap: one reviewer per file group (`--files`), in parallel, together covering every PR file.
- After a fix commit: `--review-pr <PR> --delta`. The delta reviewer answers for each open finding (fixed `yes` with the lines as evidence, else `no` or `unsure`) and ties each numbered hunk to the finding it fixes; a hunk that also changes anything else stays uncovered until a review at its file's tier reads it. A fix rewriting over half of an existing file (refused) or changing the design needs a full review. A low-tier delta is approve-only like a low-tier full review.
- Findings belong to the PR. A resolution counts only on the history that holds its head, so a fix on another branch closes nothing; a clause FAIL is resolved only by a review whose files hold the files of the review that raised it. After a force-push, a rebase or a moved merge base, every unresolved finding is carried into the next packet with its head and reproduction; answer `yes` when the current code no longer has the defect or the affected behavior. The dispatcher refuses a full review past its cap of reviewed heads without `--user-approved "<their words>"`; more reviews of a head already reviewed (file groups, a second reviewer) finish its round.
- `--pr-status <PR>` exits 0 only when it prints `REVIEWED at <tier>`: no open finding, and every file covered at its needed tier by a review that read it, or excluded. A review counts at the lower of its tier and its reviewer's rank (flash low, `concord:reviewer-opus55` high); owner words never raise it. Otherwise the status names the open findings; either way it lists every file with the review that covers it, `waived by owner`, or the tier it still needs. Reviewers see every text file as text, whatever the repository's diff attributes say; a binary file is never covered by a review and needs `--exclude` with the owner's words naming it. A retarget or a base merge that moves the merge base leaves the earlier reviews uncredited.
- `--exclude <path>` needs `--user-approved "<the owner's words naming that path>"`; it holds for that base and head only, and the status reads `REVIEWED at <tier> WITH OWNER WAIVER: <files> excluded`.
- Others' PR: findings go to the author; another engineer approves; never merge.

## 7. Report, DAT and KB
- Per phase: executor, model, billing, risk, verdict and cause, acceptance evidence, checks skipped, review verdict, findings fixed and left, files.
- `concord.py --report --plan <PLAN>` writes `REPORT_<ticket>-<id>.md` (`<id>`: the first 8 characters of the ticket id) in the runs root (`.git/concord/reports/`) from recorded data: first the Overrides (forced PASS with its failed commands, `--user-approved` texts and their use, exclusion waivers, `--no-baseline`, unsandboxed executor runs, PASS over out-of-scope or plan-modified changes, phases reviewed below their Risk), then phases, the plan's Test plan, test lines beside the `Tests:` estimate, reviews, each finding's outcome with its round, head and closing review, open items for the DAT and time against the ETA. It refuses (exit 2) while a run of the plan is open or has no verdict. It stops the drift clock, and later runs of the plan are refused (exit 10). Give the user its path for the DAT; DAT fixes take the small-fix path (scoped tests, one cheap delta review).
- KB step: replace stale lines in the repo notes and memory (never append a duplicate), run the repo notes' `KB command:` if one is set, and merge the approved case diff into the `Cases:` file (executor phases may not list it).
