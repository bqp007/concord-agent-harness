# The Concord review gate

## Phase reviews
- Tier = the phase's `Risk:` (default medium), raised for matching non-test files by a repo-notes `Risk floor <tier>: <globs>` line. low: `concord.py --review <run>` (flash), approve-only: it judges BLOCKER and HIGH only, keeps a MEDIUM it reports as a note, and its clean verdict reads `CLEAN at low (BLOCKER and HIGH only)`. medium, high: `--review <run> --packet`, a fresh `reviewer-opus55` agent per round (each Concord agent is spawned by the name the Concord rules in CLAUDE.md give it), `--review-record` its answer with `--tokens <the agent's total_tokens>`. High also takes `concord.py --review <run>` (flash), started at the same time: a model from another family has other blind spots than Opus, and its findings join the same list. Each file of the graded change needs a review at the phase's tier that read it, and at high also a flash review that read it; the report lists every file short of that under Overrides. Deleted files are part of every phase review; a binary file, or one cut at the packet cap, counts as not reviewed. Over the packet cap: `--files <globs>` per group. `--review-record` takes the rank and the model family from `--reviewer`, so name the agent that wrote the answer.
- Loop: a full review → fixes → a delta review of the fix; you track which findings it shows fixed, since the dispatcher closes findings only at the PR gate; whatever the delta does not explain, and any change an earlier review may not cover, needs a review at its own tier; stop at 0 open BLOCKER, HIGH and clause FAIL. Fix BLOCKER and HIGH after reading the cited lines, and a MEDIUM only when it occurs in a real flow; the other MEDIUMs and the NOTEs go to the test report. Every delta review runs on flash, else on the `reviewer-delta` agent (Haiku; Sonnet for a large delta), never on Opus.
- Large or risky work is reviewed from its first coherent snapshot, with your own checks beside it: review a fork (`wt.py fork <TICKET> <N>` with a number no phase uses), Monitor `<packet>.stream` and fix each streamed finding in the ticket worktree as it lands (small: here, else its executor, `--extra`); later edits get a delta review (one after the final verdict) or a re-review.
- A defect found after the gate (a later review, a PR comment, production) is fixed with a test or lint that fails on the old code, never a REVIEW.md line.

## PR gate
- Review the PR's diff from its merge base to its current head. Each file needs the highest `Risk:` of this PR's runs that changed, created or deleted it (medium when no run touched it; never below a repo-notes floor). A tier below medium also needs the PR's commits to make the file's change as a chain of transitions, each made exactly by such a run whose unforced PASS judged that candidate. `--review-pr <PR>` runs at the highest needed tier of its files; `--tier <T>` below a file's need is refused. Phase reviews do not count here.
- `--review-pr <PR>` runs flash; `--packet` for `reviewer-opus55`; a PR with a high-tier file takes both, at the same time. Over the cap: one reviewer per file group (`--files`), in parallel, together covering every PR file.
- After a fix commit: `--review-pr <PR> --delta`. The delta reviewer answers for each open finding (fixed `yes` with the lines as evidence, else `no` or `unsure`) and ties each numbered hunk to the finding it fixes; a hunk counts only in a file within that finding's scope (its file, the files of the review that raised a clause FAIL, or the whole diff when its path names no file of it), and a hunk that also changes anything else stays uncovered until a review at its file's tier reads it. A fix that rewrites a file (refused: `git diff --numstat` shows at least 40 lines added and removed, and the added or the removed lines are more than half of the file at the delta's base; binary and non-UTF-8 files never count) or changes the design needs a full review. A low-tier delta is approve-only like a low-tier full review.
- Findings belong to the PR. A resolution counts only on the history that holds its head, so a fix on another branch closes nothing; a clause FAIL is resolved only by a review whose files hold the files of the review that raised it. After a force-push, a rebase or a moved merge base, every unresolved finding is carried into the next packet with its head and reproduction; answer `yes` when the current code no longer has the defect or the affected behavior. A resolution is tied to heads, not to the merge base. The dispatcher refuses a full review past its cap of reviewed heads without `--user-approved "<their words>"`; more reviews of a head already reviewed (file groups, a second reviewer) finish its round.
- `--pr-status <PR>` exits 0 only when it prints `REVIEWED at <tier>`: no open BLOCKER, HIGH or clause FAIL, and every file covered at its needed tier by a review that read it, or excluded. A review counts at the lower of its tier and its reviewer's rank (flash low, `reviewer-opus55` high); owner words never raise it. A high-tier file also needs a review from another model family (flash) that read it at this head or whose coverage carried to it, the way any coverage carries. Otherwise the status names the open findings; either way it lists every file with the review that covers it, `waived by owner`, or the tier it still needs. Reviewers see every text file as text, whatever the repository's diff attributes say; a binary file is never covered by a review and needs `--exclude` with the owner's words naming it. A retarget (another base branch) or a base merge leaves the earlier reviews uncredited. A PR with no changed file prints `NO CHANGES` and a closed or merged one `NOT OPEN`, both with exit 1. Reviews recorded by 3.3.0 or earlier are credited under that version's rules.
- `--exclude <path>` needs `--user-approved "<the owner's words naming that path>"`; it holds for that base and head only, and the status reads `REVIEWED at <tier> WITH OWNER WAIVER: <files> excluded`. When every flash model is out at the high tier, REVIEWED waits; the owner's waiver is that `--exclude`, with words that name the file and the missing review; it drops the file from every review requirement at that head, and the report lists it with those words. A PR whose files are all binary takes `--review-pr <PR> --exclude <files> --user-approved "<words naming them>"`: no review runs, and the status reads `REVIEWED WITH OWNER WAIVER`.
- Others' PR: findings go to the author; another engineer approves; never merge.
