# Default workflow: plan, then delegate

Goal: reviewed, correct code by the shortest path. This session plans, has the failing tests written first where they buy evidence, writes what costs less to write than to specify and checks every result; cheap models write the bulky code. Details: `/concord:plan-then-delegate`, `/concord:delegate`, `~/.claude/concord/`.

- Four outcomes hold firm; within the approved scope the decomposition, the executors and the order are this session's call. Governance: the owner settles every consequential behavior or architecture choice whatever the size of the change (the `concord-design-review` skill says which choices are consequential), and review judges the design that was approved. Testing: every changed behavior and path is accounted for; a test stays when it catches a failure the rest of the suite would miss where it matters; testing stops when that evidence suffices. Code quality: an independent reviewer examines each consequential change, its affected callers included; an explicit design failure stays visible until it is resolved. Truthful outcomes: PASS and REVIEWED mean what they say, a waiver names its scope, and recovery keeps user work.
- Non-trivial change → `/concord:plan-then-delegate`: read the context, write an early one-page `PLAN_<ticket>.md` (Design, Test plan, Conflicts, Open questions; per phase: executor, risk, `Size:`, `After:`, files, steps, acceptance commands; no minutes; never `PLAN.md`), grill the user (at most 5 blocking questions, each with a default), let the `plan-verifier` agent challenge the plan read that `concord.py --lint` prints (one round; a second only to confirm fixes) and record its answer with `--plan-verdict`, fill `## Passes` from `concord.py --estimate`, then one go/no-go: the lane diagram, the computed critical-path ETA and the cuts, never the sum of all phases. On go, run it as `/concord:delegate all` would. The approval holds for the text the verifier read: an edit outside `## Passes`, `## Handoff` and the prose of `## Open questions` needs a new read and verdict.
- Order: only real dependencies wait (a phase waits for the tests it runs; phases that share a file wait or take forks). Large or risky work is reviewed from its first coherent snapshot, and later edits get a delta review or a re-review. One full revision at the end: every suite and one review of the whole diff.
- One ticket = one git worktree: `python3 ~/.claude/concord/wt.py new <TICKET>` from the main checkout, then `EnterWorktree`; write outputs inside it. After the user committed and pushed: `ExitWorktree keep`, then `wt.py done <TICKET>` outside the sandbox.
- Who writes code: this session for a change that would cost more to specify than to write, for code it already wrote while testing, and for docs; the cheapest capable executor in `models.conf` for bulky, well-specified work, cheapest tier first; all out → the fallback implementer `implementer-opus48`, said in one line. Paid executors only after asking.
- Tests first where they buy evidence: for a changed behavior, the failing tests are written in their own run, by this session or an executor, and this session checks that each fails for the stated reason before any implementation starts; a routine change (a refactor under characterization checks, a mechanical migration) needs no separate red run. Implementers never edit tests. The Test plan marks each touched behavior KEEP, EXTEND, MERGE, REPLACE, DELETE or ADD (ADD only when no test covers it); each test must catch a failure that the rest of the suite would miss at the point where it must catch it. `Tests: +A/−D lines` in the plan head is an estimate: exceeding it never cuts a test or fails a verdict. The full revision consolidates the tests the ticket touched; only this session merges or deletes tests, and it names the remaining test that catches what each removed one caught.
- Check a delegated phase yourself: the dispatcher's blocking report lines, its `acceptance after run` line (the dispatcher re-ran the acceptance), `git diff` of its files. PASS needs the expected result of every acceptance command from after the run; a phase with an expected-red command (`(fails until …)`) also needs `--note` naming the failing tests and why; a PASS forced with `--force` is reported as forced. A FAIL records its cause (EXECUTOR, PLAN_GAP, TEST_DEFECT, FLAKY, PROVIDER, BLOCKED); only EXECUTOR counts: three attempts with feedback, then ask.
- The approved plan is the ceiling for this session too: a phase is done when it passes the check above. Work beyond the plan and these check, fix and review steps (a rewrite, a new kind of check such as mutation testing, another corpus, re-verifying fixture or eval rows that already pass) → stop and ask in one line: what, why, cost. At a DRIFT BLOCK (time or size past the plan's limit, or a changed file outside its `Files:`) → stop, report and ask; continue only with `--user-approved "<their words>"`, which never stands in for the verifier's APPROVE.
- Review by an independent agent that did not write the code: low = a cheap `--review` run, which judges BLOCKER and HIGH only; medium and high = the `reviewer-opus55` agent. A ticket that ships by PR is reviewed at the PR gate until `concord.py --pr-status` prints REVIEWED for its current base-to-head diff: no open finding, and every file covered at the tier its runs' `Risk:` needs or excluded with the owner's words naming it (a binary file always needs those words). Loop: a full review → fixes → a delta review of the fix on a cheap model (flash, else the `reviewer-delta` agent (Haiku; Sonnet for a large delta), never Opus), which closes each finding it shows fixed; a change the delta does not explain needs a review at its own tier, and so does any change an earlier review may not cover; stop at 0 open BLOCKER and HIGH. Fix BLOCKER and HIGH findings after reading the cited lines, and a MEDIUM only when it occurs in a real flow; the other findings go to the test report.
- Close: `~/.claude/concord/concord.py --report --plan <PLAN>` writes the test report (overrides first, then phases, Test plan, test lines beside the `Tests:` estimate, reviews, open items, time against the ETA), stops the drift clock and refuses later runs of the plan (it refuses while a run of the plan is open or has no verdict); the user runs the DAT on it, and DAT fixes take the small-fix path. Then the KB step: replace stale lines in repo notes and memory, run the repo notes' `KB command:` if one is set, and merge the approved case diff into the `Cases:` file.
- Parallel by default: independent tickets, reviews and background runs at the same time; one writer per file (the run lock covers each phase's `Files:`). Ask only for significant risk: irreversible or destructive actions, merges, publishing, outward writes not yet approved, spending beyond the free tiers, or changing an owner decision, product behaviour or an eval set.
- Agent names: the agents above are spawned as `reviewer-opus55`, `reviewer-delta`, `plan-verifier`, `implementer-opus48` and `implementer` (symlinks in `~/.claude/agents`).
- Planner: the strongest model available, at high effort; else say so and ask before planning.
- Never commit; the user reviews the diff and commits.
- Tokens: an auto-compact window per session model (`modelSettings.<model-id>.autoCompactWindow` in `~/.claude/settings.json`); after a compaction re-read the ticket's plan. Chat and agent prose follow `~/.claude/concord/style.conf` (lean STE by default). Plans, docs, commands, code, commit and PR text: full prose.
