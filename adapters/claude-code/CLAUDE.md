# Default workflow: plan, then delegate

Goal: reviewed, correct code by the shortest path. This session plans, writes the tests and the small changes, and checks results; cheap models write the bulky code. Details: `/concord:plan-then-delegate`, `/concord:delegate`, `~/.claude/concord/`.

- Non-trivial change → `/concord:plan-then-delegate`: read the context, write an early one-page `PLAN_<ticket>.md` (Design, Test plan, Conflicts, Open questions; per phase: executor, risk, `Size:`, `After:`, files, steps, acceptance commands; no minutes; never `PLAN.md`), grill the user (at most 5 blocking questions, each with a default), let the `plan-verifier` agent challenge it (one round; a second only to confirm fixes), fill `## Passes` from `concord.py --estimate`, then one go/no-go: the lane diagram, the computed critical-path ETA and the cuts, never the sum of all phases. On go, run it as `/concord:delegate all` would.
- Passes, not a chain: after the failing tests, pass 1 starts every phase at once at rough quality; later passes fix only the largest gaps; each pass re-runs only its own acceptance; one full revision at the end: every suite and one review of the whole diff.
- One ticket = one git worktree: `python3 ~/.claude/concord/wt.py new <TICKET>` from the main checkout, then `EnterWorktree`; write outputs inside it. After the user committed and pushed: `ExitWorktree keep`, then `wt.py done <TICKET>` outside the sandbox.
- Who writes code: this session for tier S (60 lines or fewer and 3 files or fewer), for code it already wrote while testing, and for docs; the cheapest capable executor in `models.conf` for bulky, well-specified work, cheapest tier first; all out → the fallback implementer `implementer-opus48`, said in one line. Paid executors only after asking. sonnet/haiku/opus only as the `implementer` subagent (`~/.claude/concord/concord.py` enforces this).
- Tests first, by this session; implementers never edit tests. A delegated phase's acceptance must fail on the untouched code (red run) unless marked `(characterization)`. The plan head carries `Tests: +A/−D lines, net ≤ N`; the Test plan marks each touched behavior KEEP, EXTEND, MERGE, REPLACE, DELETE or ADD (ADD only when no test covers it); a finding fix adds at most one row; the last pass consolidates the tests the ticket touched; only this session merges or deletes tests.
- Check a delegated phase yourself: the dispatcher's blocking report lines, its `acceptance after run` line (the dispatcher re-ran the acceptance), `git diff` of its files. A FAIL records its cause (EXECUTOR, PLAN_GAP, TEST_DEFECT, FLAKY, PROVIDER, BLOCKED); only EXECUTOR counts: three attempts with feedback, then ask.
- The approved plan is the ceiling for this session too: a phase is done when it passes the check above. Work beyond the plan and these check, fix and review steps (a rewrite, a new kind of check such as mutation testing, another corpus, re-verifying fixture or eval rows that already pass) → stop and ask in one line: what, why, cost. At a DRIFT BLOCK (time or size at 1.5× the plan, or a changed file outside its `Files:`) → stop, report and ask; continue only with `--user-approved`.
- Review by an independent agent that did not write the code: low = a cheap `--review` run, medium and high = the `reviewer-opus55` agent. A ticket that ships by PR is reviewed at the PR gate: its full diff at its tier on its current head, until `concord.py --pr-status` prints REVIEWED. Loop: a full review → fixes → a delta review of the fix on a cheap model (flash, else the `reviewer-delta` agent (Haiku; Sonnet for a large delta), never Opus) → a full review of the new head; stop at 0 BLOCKER and 0 HIGH, at most 3 full reviews (a 4th needs `--user-approved`). Fix BLOCKER and HIGH findings after reading the cited lines, and a MEDIUM only when it occurs in a real flow; the other findings go to the test report.
- Close: `concord.py --report --plan <PLAN>` writes the test report (phases, Test plan, test lines, reviews, open items, time against the ETA) and stops the drift clock; the user runs the DAT on it, and DAT fixes take the small-fix path. Then the KB step: replace stale lines in repo notes and memory, run the repo notes' `KB command:` if one is set, and merge the approved case diff into the `Cases:` file.
- Parallel by default: independent tickets, reviews and background runs at the same time; one writer per file (the run lock covers each phase's `Files:`). Ask only for significant risk: irreversible or destructive actions, merges, publishing, outward writes not yet approved, spending beyond the free tiers, or changing an owner decision, product behaviour or an eval set.
- Agent names: the agents above are spawned as `reviewer-opus55`, `reviewer-delta`, `plan-verifier`, `implementer-opus48` and `implementer` (symlinks in `~/.claude/agents`).
- Planner: the strongest model available, at high effort; else say so and ask before planning.
- Never commit; the user reviews the diff and commits.
- Tokens: an auto-compact window per session model (`modelSettings.<model-id>.autoCompactWindow` in `~/.claude/settings.json`); after a compaction re-read the ticket's plan. Chat and agent prose follow `~/.claude/concord/style.conf` (lean STE by default). Plans, docs, commands, code, commit and PR text: full prose.
