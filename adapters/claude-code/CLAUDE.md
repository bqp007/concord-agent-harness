# Default workflow: plan, then delegate

Goal: reviewed, correct code by the shortest path. This session plans, writes the tests and the small changes, and checks results; cheap models write the bulky code. Details: `/concord:plan-then-delegate`, `/concord:delegate`, `~/.claude/concord/`.

- Non-trivial change → `/concord:plan-then-delegate`: a one-page `PLAN_<ticket>.md` in passes (per phase: executor, risk, files, steps, acceptance commands; never `PLAN.md`), open questions settled by the user, stop for approval, then run it as `/concord:delegate all` would. Plans shown for approval carry a schedule diagram (one lane per run that goes at the same time) and the critical-path ETA, never the sum of all phases.
- Passes, not a chain: after the failing tests, pass 1 starts every phase at once at rough quality; later passes fix only the largest gaps; each pass re-runs only its own acceptance; one full revision at the end: every suite and one review of the whole diff.
- One ticket = one git worktree: `python3 ~/.claude/concord/wt.py new <TICKET>` from the main checkout, then `EnterWorktree`; write outputs inside it. After the user committed and pushed: `ExitWorktree keep`, then `wt.py done <TICKET>` outside the sandbox.
- Who writes code: this session for changes up to about 60 lines, for code it already wrote while testing, and for docs; the cheapest capable executor in `models.conf` for bulky, well-specified work, cheapest tier first; all out → the fallback implementer `implementer-opus48`, said in one line. Paid executors only after asking. sonnet/haiku/opus only as the `implementer` subagent (`~/.claude/concord/concord.py` enforces this).
- Tests first, by this session; implementers never edit tests. A delegated phase's acceptance must fail on the untouched code (red run) unless marked `(characterization)`.
- Check a delegated phase yourself: the dispatcher's blocking report lines, the acceptance commands re-run here, `git diff` of its files. A FAIL records its cause (EXECUTOR, PLAN_GAP, TEST_DEFECT, FLAKY, PROVIDER, BLOCKED); only EXECUTOR counts: three attempts with feedback, then ask.
- The approved plan is the ceiling for this session too: a phase is done when it passes the check above. Work beyond the plan and these check, fix and review steps (a rewrite, a new kind of check such as mutation testing, another corpus, re-verifying fixture or eval rows that already pass) → stop and ask in one line: what, why, cost. A phase past twice its estimated minutes → stop, report, ask, even with attempts left.
- Review once, by an independent agent that did not write the code: low = a cheap `--review` run, medium and high = the `reviewer-opus55` agent. A ticket that ships by PR is reviewed at the PR gate: its full diff at its tier on its current head, until `concord.py --pr-status` prints REVIEWED. Fix confirmed BLOCKER/HIGH/MEDIUM findings right away (confirm by reading the cited lines), re-review the fix once (delta); still open after two fix rounds → ask. NOTE findings go in the report.
- Parallel by default: independent tickets, reviews and background runs at the same time; one writer per checkout. Ask only for significant risk: irreversible or destructive actions, merges, publishing, outward writes not yet approved, spending beyond the free tiers, or changing an owner decision, product behaviour or an eval set.
- Agent names: the agents above are spawned as `reviewer-opus55`, `implementer-opus48` and `implementer` (symlinks in `~/.claude/agents`).
- Planner: the strongest model available, at high effort; else say so and ask before planning.
- Never commit; the user reviews the diff and commits.
- Tokens: an auto-compact window per session model (`modelSettings.<model-id>.autoCompactWindow` in `~/.claude/settings.json`); after a compaction re-read the ticket's plan. Chat and agent prose follow `~/.claude/concord/style.conf` (terse by default). Plans, docs, commands, code, commit and PR text: full prose.
